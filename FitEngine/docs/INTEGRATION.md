# دليل الدمج المستقبلي

> **تحديث 2026-10-17:** تم فحص موديول الأفاتار (براءه، `Project_Workspace` commit `fd94a8b`) وكتابة `fit_engine/adapters.py` لجهة قياسات الجسم. انظر "الربط مع الأفاتار" في آخر الملف. جهة الملابس (سجى) لم تُربط بعد.
> كل ما يلي **عقد مقترح** يجب الاتفاق عليه مع الفريق قبل الربط. لا تُعدّل مشاريع الزميلات لتناسب هذا النظام؛ الأسهل أن تُكتب طبقة تحويل صغيرة (adapter) عندنا.

## الصورة العامة

```
نظام الأفاتار (براءه)          نظام إدارة الملابس (سجى)
  قياسات جسم المستخدم              بيانات القطعة + قياسات كل مقاس
          │                                  │
          └────────────┬─────────────────────┘
                       ▼
             fit_engine.recommend_size(body, garment)
                       │
                       ▼
     المقاس الموصى به + التقييم لكل منطقة + البديل + التحذيرات
                       │
                       ▼
     واجهة المستخدم / عرض القطعة على الأفاتار (عرض بصري منفصل)
```

التوصية الرقمية والعرض البصري على الأفاتار **شيئان منفصلان**: الأفاتار يمكن أن يعرض المقاس الموصى به، أو يلوّن المناطق الضيقة/الواسعة باستخدام `comparisons[].status`، لكن قرار المقاس لا يعتمد على الموديل ثلاثي الأبعاد.

## طرق الاستدعاء

| الطريقة | متى تُستخدم |
|---|---|
| `from fit_engine import recommend_size` | إذا كان الـ backend مكتوبًا بـ Python |
| `POST /recommend` على `python -m fit_engine serve` | إذا كان الـ backend بلغة أخرى (Node.js مثلًا) أو للاختبار من الواجهة |
| `python -m fit_engine recommend --body ... --garment ...` | للتجربة اليدوية وتصحيح الأخطاء |
| واجهة الويب `http://127.0.0.1:8765/` | لتجربة الخوارزمية يدويًا أو لصق JSON بصيغة العقد للتحقق من بيانات الزميلتين لاحقًا |

منطق الاقتراح كله في `engine.py` و`rules.py` و`validation.py`. الواجهة (`web/index.html`) والـ API (`server.py`) وسطر الأوامر (`cli.py`) طبقات عرض فقط تستدعي `recommend_size` ولا تحتوي أي منطق مقاسات. لذلك يمكن ربط الموديول بواجهة المنصة النهائية دون استخدام واجهتنا.

الـ API المحلي مخصص للتطوير: يعمل على `127.0.0.1` وبدون مصادقة. للنشر الفعلي يُنصح بوضع الدالة داخل backend المشروع أو خلف خادم مناسب (مثل FastAPI) بعد موافقة الفريق.

## ما المطلوب من نظام الأفاتار (براءه)

إرسال كائن بهذا الشكل (أو كتابة adapter يحوّل شكلها إليه):
```json
{"user_id": "...", "source": "avatar", "unit": "cm",
 "measurements": {"height": 0, "chest": 0, "waist": 0, "hip": 0,
                  "shoulder_width": 0, "arm_length": 0, "inseam": 0, "thigh": 0}}
```
أسئلة يجب الاتفاق عليها:
1. ما القياسات التي ينتجها نظامها فعلًا؟ (أي قياس ناقص يُعالج تلقائيًا ويخفض الثقة.)
2. ما وحدة القياس، وهل هي محيطات حقيقية أم تقديرات؟
3. هل `shoulder_width` عندها من رأس الكتف لرأس الكتف (مثل تعريفنا)؟
4. إذا كانت أسماؤها مختلفة: نضيفها لجدول `BODY_ALIASES` في `schema.py` بدل تغيير كودها.

## ما المطلوب من نظام الملابس (سجى)

لكل منتج:
- `category` من القائمة المدعومة، أو نضيف نوعًا جديدًا في `rules.py`.
- `fit_type` و`stretch` إن توفرت (غيابهما مسموح لكنه يخفض الثقة).
- قياسات **فعلية** لكل مقاس، مع تحديد إن كانت محيطًا كاملًا أو مسطّحة (`measurement_type`).
- ترتيب المقاسات من الأصغر للأكبر.
- اختياري: `ease_overrides` إذا كان للمنتج نطاق راحة معروف من المصنّع.

أسئلة يجب الاتفاق عليها:
1. شكل تخزين المقاسات في قاعدة بياناتها وأسماء الحقول.
2. هل القياسات من جدول مقاسات عام أم قياسات فعلية للقطعة؟ (الأفضل فعلية.)
3. كيف تُحفظ مرونة القماش والقصة؟ نحتاج تحويلها إلى القيم المدعومة.

## خطوات الدمج المقترحة (بعد الإذن الصريح)
1. اجتماع قصير للاتفاق على أسماء الحقول والوحدات (الجداول في `DATA_MODEL.md`).
2. كتابة `adapters.py` عندنا: `avatar_to_body(...)` و `catalog_to_garment(...)`.
3. اختبار على عينة من بيانات الزميلتين الحقيقية دون تعديل مشاريعهما.
4. ربط نقطة واحدة في الواجهة: "اقترح لي مقاسًا".
5. تجارب قياس حقيقية (انظر `REPORT.md`) ثم ضبط قيم `rules.py`.

## متطلبات تقنية للدمج
- Python 3.9 أو أحدث. لا مكتبات خارجية.
- الدالة نقية وحتمية (نفس المدخلات = نفس المخرجات)، بدون قاعدة بيانات أو حالة داخلية، وآمنة للاستدعاء المتوازي.
- لا تُرمى استثناءات على مدخلات خاطئة؛ النتيجة تحمل `status: "invalid_input"` و`errors`.
- رقم الإصدار في `engine_version` لتتبع تغيّر القواعد.

## الربط مع الأفاتار — ما نُفّذ (2026-10-17)

`fit_engine/adapters.py` → `avatar_to_body(avatar)` يقبل **طلب** أو **رد** `POST /generate-avatar` (منفذ 8002) ويعيد مستند جسم لـ `recommend_size`. متاح أيضًا عبر `POST /avatar-to-body` وفي الواجهة (قسم "تعبئة القياسات من الأفاتار").

**القرار:** تُستخدم القياسات التي **أدخلها المستخدم** (الطلب، أو `accuracy[*].requested` في الرد)، وليس قياسات الموديل المتولّد. السبب: الموديل قد يبتعد عن الطلب؛ في رد حقيقي (الوزن 150 كغ) كان صدر الموديل 101.6 سم والمطلوب 90 سم.

| الأفاتار | fit_engine | ملاحظة |
|---|---|---|
| `chest`, `waist`, `hip` | نفس الاسم | محيطات بالسم |
| `height` | `height` | للفحص فقط |
| `shoulder` (ذكور فقط) | `shoulder_width` | نفس التعريف: رأس الكتف لرأس الكتف عبر الظهر |
| `weight` | — | يُتجاهل |
| `measurements.shoulder_width_m`, `arm_length_m`, `leg_length_m` | — | **لا تُستخدم**: مسافات بين مراكز المفاصل، وليست قياس متر |

**رابط مباشر:** `http://127.0.0.1:8020/?avatar_id=<id>&height=..&chest=..&waist=..&hip=..&shoulder=..` يفتح الواجهة وقياسات الجسم معبّأة (عبر `POST /avatar-to-body`). زر مقترح لصفحة الأفاتار يستخدم هذا الرابط موجود في مشروع الفريق: `FitEngine/integration/` (غير مطبَّق؛ القرار لبراءه).

**لماذا لا يوجد زر "اقترح مقاسًا" تلقائي من صفحة الأفاتار:** موديول الأفاتار لا يوفّر endpoint لقراءة قياسات أفاتار سابق بالـ id (القياسات تأتي مرة واحدة في رد التوليد، وصفحة براءه تحفظها في localStorage خاص بها). ربط بنقرة واحدة يحتاج أحد هذين، **بقرار من براءه**:
1. `GET /avatars/{avatar_id}/measurements` في الـ API، أو
2. زر في صفحتها يرسل الطلب إلى `POST /avatar-to-body` ثم `POST /recommend`.

**ما زال مفتوحًا — جهة الملابس (سجى):** لا يوجد جدول مقاسات (S/M/L مع قياسات كل مقاس) في موديول الملابس؛ قياس القطعة من الصورة يعطي قطعة واحدة وليس كل المقاسات. لذلك ما زالت المقاسات تُدخل يدويًا أو بصيغة `DATA_MODEL.md`.
